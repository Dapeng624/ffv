# AI 视频生成工作台开发规则文档

> 文档版本：V1.0  
> 适用阶段：MVP 设计、开发、测试与上线  
> 关联文档：[MVP 产品需求文档](./mvp-prd.md)

> 核心功能范围：[核心功能复刻范围](./core-function-spec.md)

## 1. 文档目的

本文件是项目后续设计和开发的统一约束。产品、设计、前端、后端和测试在需求存在歧义时，应优先遵循本文件与 MVP PRD；两者冲突时，以最新确认的产品决策为准，并同步修改文档。

MVP 的唯一核心闭环是：

用户登录 -> 上传一张图片 -> 选择视频模板 -> 设置必要参数 -> 消耗积分并提交任务 -> 等待生成 -> 预览 -> 下载或再次生成。

任何不能直接提升该闭环完成率、生成成功率或付费转化率的功能，默认不进入 MVP。

## 2. 产品原则

### 2.1 用户优先级

按以下顺序服务用户：

1. 有商品图片、希望生成广告素材的电商商家。
2. 有门店或服务图片、希望生成宣传素材的本地商家。
3. 有人物或角色图片、希望生成短视频的内容创作者。

### 2.2 产品体验原则

- 结果优先：用户进入产品后，应在首屏直接看到生成器，而不是品牌宣传长页。
- 模板优先：先让用户选择可理解的商业场景，再暴露模型和高级参数。
- 最少输入：默认值必须足以完成一次生成；高级参数不能阻塞主流程。
- 成本透明：提交前必须显示本次消耗积分，失败后必须明确退款状态。
- 状态可见：耗时操作必须提供清晰状态，禁止无反馈等待。
- 可恢复：刷新页面、关闭浏览器或重新登录后，任务及结果不能丢失。
- 商业可用：下载的视频、比例、水印和授权信息必须明确，不把关键限制藏在结果页之后。

### 2.3 MVP 范围控制

以下能力不进入第一版主流程：

- 多轨时间线编辑器
- 复杂字幕、配音和音频编辑
- 团队协作与成员权限
- 多模型横向比较
- 批量生成与批量下载
- 开放 API
- 移动端原生应用
- 长视频与连续剧情生成

如需新增范围，必须同时说明目标用户、核心指标、开发成本和被替换的现有优先级。

## 3. 参考网站与原创边界

页面信息架构和交互节奏可参考 Higgsfield 一类 AI 视频工作台，重点借鉴：

- 顶部全局导航与账户区域
- 首屏直接呈现生成入口
- 大尺寸媒体预览与紧邻的生成参数面板
- 横向分类导航与视觉化模板列表
- 模板即入口，点击后自动带入生成参数
- 生成历史和作品管理形成持续创作闭环

不得直接复制：

- 对方品牌名、Logo、商标和品牌口号
- 原站文案、模板名称、示例素材和视频
- 具有明显识别度的插画、图标、动效和视觉资产
- 完全相同的颜色、字体、间距和组件细节组合
- 对方受保护的前端代码、接口和数据

最终产品应拥有独立品牌、独立设计令牌、独立文案和合法来源的演示素材。参考目标是相似的使用逻辑，不是像素级复刻。

## 4. 页面结构规则

### 4.1 全局导航

桌面端顶部导航固定包含：

- 品牌入口
- 生成
- 模板
- 我的作品
- 价格
- 积分余额
- 用户菜单

规则：

- “生成”始终是视觉优先级最高的主入口。
- 当前页面必须有明确选中状态。
- 积分余额必须在提交生成前可见。
- 移动端收起次要导航，但保留品牌、积分和用户入口。
- 导航中不放尚未开放或点击后无内容的入口。

### 4.2 首页与生成页

首页即生成工作台，不单独制作传统营销落地页。桌面端采用“媒体输入/预览区 + 参数控制区”的主结构，模板推荐紧随其后；移动端按“预览、参数、生成按钮、模板”的顺序单列排列。

首屏必须包含：

- 图片上传区或当前素材预览
- 模板选择入口
- Prompt 输入框
- 视频比例
- 视频时长
- 本次积分消耗
- 生成按钮

首屏规则：

- 页面打开后 10 秒内，首次用户应能理解如何开始生成。
- 主操作按钮在常用桌面和移动视口中容易找到。
- 高级参数默认折叠。
- 模型仅有一个时不显示模型选择器。
- 上传成功后立即显示缩略图、替换和删除操作。
- 未满足提交条件时禁用生成按钮，并说明唯一、具体的缺失项。

### 4.3 模板页

模板页采用分类筛选加媒体卡片列表，优先展示视频预览，不使用大量说明文字。

每张模板卡片至少展示：

- 封面或静音循环预览
- 模板名称
- 适用类型
- 默认比例和时长
- 预计积分
- “使用模板”操作

规则：

- 点击卡片进入详情或预览；点击“使用模板”直接进入生成器并带入参数。
- 分类第一版固定为商品广告、人物短片、门店宣传、热门特效、社媒内容。
- 首屏视频只加载封面，进入可视区域后再加载预览，避免一次加载全部视频。
- 所有模板必须配置素材类型、默认 Prompt、默认参数和适配模型。
- 没有预览素材的模板不得发布。

### 4.4 任务与结果页

任务详情页必须展示输入、参数、费用和状态。成功后，以结果视频为视觉主体。

必须支持以下状态：

- `queued`：等待中
- `processing`：生成中
- `succeeded`：生成成功
- `failed`：生成失败
- `refunded`：失败且积分已退回

规则：

- 等待和生成状态显示阶段文案及创建时间，不伪造精确百分比。
- 页面刷新后从服务端恢复状态。
- 成功状态提供预览、下载、再次生成和查看参数。
- 失败状态提供失败原因、积分处理结果和再次尝试入口。
- 后端状态未知或网络中断时显示“状态同步中”，不能直接判定失败。

### 4.5 我的作品

默认按创建时间倒序展示当前用户的生成记录。

第一版支持：

- 按全部、生成中、成功、失败筛选
- 查看任务详情
- 预览成功视频
- 下载成功视频
- 使用相同参数再次生成
- 删除记录

删除前必须二次确认。删除记录是否同时删除云端文件，应在确认文案中明确。

### 4.6 价格页

价格页以可生成的典型视频数量解释积分，不只展示抽象积分数。

每个方案必须明确：

- 价格与结算周期
- 获得积分
- 约可生成的视频数量
- 水印规则
- 清晰度
- 商用权限
- 积分有效期

尚未接入支付时，价格页按钮不得伪装成可付款状态，可使用“即将开放”或申请内测。

### 4.7 管理后台

管理后台与用户端路由和权限隔离。第一版仅服务运营和故障处理，包含：

- 用户查询
- 任务查询与错误详情
- 积分人工调整及原因记录
- 模板新增、编辑、上下架
- 订单查询，接入支付后启用

后台所有积分调整、模板变更和关键任务操作必须记录操作者、时间和原因。

## 5. 视觉与交互规则

### 5.1 视觉方向

整体应像专业创作工具，而不是传统企业官网：媒体内容占主导，控制面板克制，层级清晰，适合长时间和重复使用。

- 使用中性背景搭配独立品牌强调色，避免整页只有一种色相。
- 卡片圆角不超过 8px，除头像、状态点和圆形图标按钮外不滥用胶囊形状。
- 页面区域采用自然分区，不把每个区块都包成悬浮卡片。
- 图标优先使用统一图标库，不混用多套线条风格。
- 文本和控件必须满足常见视口下无截断、无重叠、无横向溢出。
- 不使用无业务意义的渐变光球、模糊色块或装饰性大面积渐变。

### 5.2 设计令牌

开发前统一定义并集中管理：

- 品牌色、强调色、成功色、警告色、错误色
- 页面背景、面板背景、浮层背景、边框和分隔线
- 主文字、次文字、禁用文字
- 字号、行高和字重层级
- 4px 基础间距体系
- 4px、6px、8px 圆角层级
- 阴影层级
- 桌面、平板、移动端断点

组件内不得随意硬编码新的颜色、圆角、阴影和间距值。新增令牌必须说明现有令牌无法覆盖的原因。

### 5.3 响应式规则

最低支持：

- 移动端：360px 及以上
- 平板：768px 及以上
- 桌面：1280px 及以上
- 宽屏：1440px 及以上

规则：

- 桌面生成器可双栏，移动端必须单栏。
- 视频和图片预览使用固定比例容器，资源加载不得造成布局跳动。
- 触控目标建议不小于 44px。
- 不以缩小到难以阅读的字体解决空间不足。
- 横向模板列表在移动端可横滑，但关键表单不能依赖横向滚动。

### 5.4 反馈与异常

- 每个异步动作都必须有加载、成功、失败反馈。
- 表单错误靠近对应字段显示，不只使用全局提示。
- 全局提示适合确认完成，不承载长错误说明。
- 用户可修复的错误应说明下一步，例如更换图片、修改描述或稍后重试。
- 防止重复提交：任务创建过程中禁用按钮，并使用唯一请求标识保证幂等。
- 下载开始、积分变化和退款完成必须有可见反馈。

### 5.5 可访问性

- 表单字段必须有关联标签。
- 图标按钮必须有可访问名称和悬停提示。
- 键盘可完成登录、上传、填写和提交主流程。
- 焦点状态必须可见。
- 文字与背景保持足够对比度。
- 视频默认静音自动预览；必须提供播放、暂停和静音控制。

## 6. 文案规则

- 面向商家使用结果语言，例如“生成商品广告视频”，少用模型术语。
- 按钮使用明确动作：上传图片、使用模板、生成视频、下载视频、再次生成。
- 不使用“魔法”“一键颠覆”等夸张承诺。
- 不承诺绝对生成时长，可展示常见时间范围。
- 积分扣除、退款、水印和商用限制必须使用直接、无歧义的语言。
- 中文为 MVP 默认语言；字段名、错误码和后台日志可保留英文技术标识。

## 7. 前端开发规则

具体框架在项目初始化时确定。若无额外约束，推荐 TypeScript、React、Next.js 和成熟组件基础库；无论选择何种技术栈，必须遵循以下规则：

- 页面按业务域组织，不创建无边界的全局组件目录。
- 通用组件只封装稳定、重复出现的行为。
- 服务端数据、表单状态和纯 UI 状态分开管理。
- API 调用统一经过请求层，页面组件不直接拼接接口地址。
- 用户身份和权限由服务端校验，前端隐藏按钮不等于权限控制。
- 所有列表包含加载、空、错误和分页或继续加载状态。
- 图片和视频必须声明比例或尺寸，使用懒加载和合适格式。
- 用户可见错误不得直接显示第三方模型原始错误或堆栈。
- 环境变量按本地、测试、生产隔离；密钥不得进入浏览器包或代码仓库。
- 禁止在主业务页面使用仅用于演示的假按钮和无响应控件。

## 8. 后端与 API 规则

### 8.1 API 约定

- API 使用版本前缀，例如 `/api/v1`。
- 请求和响应采用稳定结构，并包含可追踪的请求 ID。
- 错误响应至少包含机器可读错误码和用户可理解信息。
- 时间统一以 UTC 存储，客户端按用户时区展示。
- 金额使用最小货币单位整数存储，积分使用整数存储。
- 列表接口必须限制单页数量并提供稳定分页。
- 创建任务、支付回调和积分变更接口必须幂等。

### 8.2 视频任务规则

任务创建顺序：

1. 校验用户、输入素材、模板和参数。
2. 计算并确认积分费用。
3. 在数据库事务中创建任务和预扣积分流水。
4. 将任务投递到队列。
5. 工作进程调用第三方模型。
6. 更新任务状态并保存输出。
7. 成功确认扣费；失败生成退款流水。

禁止在浏览器请求中同步等待视频生成完成。

任务必须保存：

- 用户 ID
- 输入资源地址及校验信息
- 原始 Prompt 与最终 Prompt
- 模板及模板版本
- 模型和参数
- 预估及实际积分
- 第三方任务 ID
- 当前状态和状态时间
- 输出资源地址
- 标准化错误码

### 8.3 第三方模型适配

- 通过统一适配层调用模型供应商，业务代码不依赖单一供应商字段。
- 对供应商设置超时、有限重试和熔断策略。
- 只有明确可重试的网络或限流错误才能自动重试。
- 回调必须验证签名；轮询必须有退避和总时限。
- 保存供应商任务 ID，便于排查，但不得向普通用户暴露内部敏感信息。
- 第三方服务异常不能造成重复扣费。

## 9. 数据与存储规则

- 数据表使用不可猜测的唯一 ID。
- 用户只能读取和操作自己的素材、任务、作品和订单。
- 上传文件与生成结果使用对象存储，不存入关系数据库正文。
- 私有素材默认使用受限访问地址或短时签名地址。
- 文件名不能作为唯一标识，需校验 MIME、扩展名和文件内容类型。
- 任务、积分、订单和审核记录采用软删除或审计保留策略。
- 模板修改必须保留版本，历史任务不能因模板更新而改变参数。
- 开发、测试和生产数据严格隔离。

建议 MVP 数据保留：

- 原始上传素材：30 天，可按套餐延长
- 生成结果：30 天，可按套餐延长
- 任务与积分流水：至少 1 年
- 订单与财务记录：按运营地区法规执行
- 安全和后台审计日志：至少 180 天

上线前必须在用户协议和产品界面中明确实际保留期限。

## 10. 积分与订单规则

积分余额不能只保存在用户表中，必须以不可随意覆盖的流水为依据。

流水类型至少包含：

- 注册赠送
- 购买充值
- 任务预扣
- 任务确认消耗
- 任务失败退款
- 运营赠送
- 运营扣减
- 订单退款扣回

规则：

- 余额不足时禁止创建任务。
- 同一任务最多产生一次有效扣费和一次对应退款。
- 后台人工修改必须填写原因。
- 价格调整不能影响已经创建的任务。
- 支付结果以服务端签名回调为准，不信任前端跳转参数。
- 订单退款与积分扣回需要处理积分已被使用的情况，并形成审计记录。

## 11. 内容安全与合规规则

提交任务前至少审核文本和上传图片；生成完成后应对结果进行必要的安全检查。

禁止内容包括：

- 色情及未成年人不当内容
- 恐怖、极端暴力和仇恨内容
- 违法交易、欺诈和危险行为指导
- 未经授权的受保护素材或明显侵权内容
- 冒充公众人物、制造误导性陈述或虚假背书
- 未经同意使用他人肖像制作欺骗性商业内容

规则：

- 用户上传前确认拥有素材和使用权。
- 被拒绝的任务不提交给模型，不扣除最终积分。
- 审核结果使用标准化原因，用户侧提供适度、可操作的解释。
- 高风险内容保留必要审核记录，访问权限受控。
- 用户协议、隐私政策、商用授权和退款政策必须在正式收费前上线。
- 不在日志中记录密码、支付凭证、完整密钥或不必要的个人数据。

## 12. 安全规则

- 密码使用成熟的强哈希方案，不自行设计加密算法。
- 身份会话使用安全 Cookie 或成熟认证方案，生产环境强制 HTTPS。
- 所有写操作校验身份、权限、参数和资源归属。
- 上传文件限制大小、类型、尺寸和频率，并进行恶意文件检查。
- 登录、注册、上传、生成和支付接口必须限流。
- 密钥只存储于服务端密钥管理或受控环境变量。
- 数据库、对象存储和后台遵循最小权限原则。
- 高风险后台操作需二次确认；条件允许时启用管理员多因素认证。
- 依赖升级和安全漏洞修复纳入发布流程。

## 13. 日志、监控与分析规则

### 13.1 业务事件

至少记录以下匿名化业务事件：

- 注册完成
- 首次上传完成
- 模板选择
- 任务提交
- 任务成功
- 任务失败
- 结果预览
- 视频下载
- 再次生成
- 查看价格
- 发起支付及支付成功，接入支付后

事件不得包含完整 Prompt、上传素材内容、邮箱或支付敏感信息。

### 13.2 系统监控

必须监控：

- API 错误率和响应时间
- 队列长度和任务等待时间
- 各模型成功率、耗时和单次成本
- 积分预扣与退款异常
- 对象存储上传和下载失败率
- 支付回调异常，接入支付后

关键告警必须能通过请求 ID、用户 ID、任务 ID 和第三方任务 ID 串联排查。

## 14. 测试与验收规则

### 14.1 自动化测试最低要求

- 积分计算、预扣、确认和退款必须有单元测试。
- 任务状态转换必须有单元测试。
- 权限和资源归属必须有接口测试。
- 创建任务幂等、第三方回调幂等必须有接口测试。
- 注册到下载的核心路径必须有端到端测试。
- 第三方模型在自动化测试中使用可控模拟，不依赖真实生成费用。

### 14.2 页面验收

每个用户页面必须检查：

- 加载、空、正常、错误、禁用状态
- 360px、768px、1280px 和 1440px 视口
- Chrome、Safari 当前主流版本
- 键盘操作和焦点状态
- 长文案、长邮箱、低积分、无封面、视频加载失败等边界情况
- 图片和视频加载前后无明显布局跳动
- 无按钮遮挡、文字溢出和不合理横向滚动

涉及视觉变更时必须通过真实浏览器截图检查桌面端和移动端。涉及视频预览时还需确认资源实际加载、画面非空、比例正确且控制可用。

### 14.3 核心业务验收

MVP 上线前必须通过：

1. 新用户能注册并收到免费积分。
2. 用户能上传合法图片并看到预览。
3. 用户能选择模板，默认参数正确带入。
4. 提交前展示准确积分费用。
5. 任务提交后刷新页面仍可继续查看。
6. 成功任务只扣一次积分并能预览、下载。
7. 失败任务自动退款且记录可追溯。
8. 用户不能访问其他用户的素材、任务和视频。
9. 管理员能定位失败任务并查看标准化错误。
10. 移动端能完整完成上传、生成和下载流程。

## 15. Git 与代码质量规则

- 受保护分支不直接提交功能代码，通过独立分支和代码审查合并。
- 分支建议使用 `feature/`、`fix/`、`chore/` 前缀。
- 每个提交只包含一个可说明的逻辑变更，避免混入无关格式化。
- 提交前运行格式化、静态检查、类型检查和相关测试。
- 不提交密钥、真实用户数据、大型生成视频、构建产物和本地环境文件。
- 数据库结构变更必须附迁移文件和回滚或兼容说明。
- API 或数据结构变更必须同步更新类型、测试和文档。
- 代码评审优先检查业务正确性、权限、扣费、失败恢复和用户数据安全。

## 16. 发布规则

采用本地、测试、生产三个独立环境。每次发布必须：

1. 通过类型检查、静态检查和自动化测试。
2. 在测试环境完成核心流程冒烟测试。
3. 确认数据库迁移向前兼容并已备份。
4. 确认第三方模型、存储、邮件和支付配置属于当前环境。
5. 检查监控、错误追踪和告警可用。
6. 记录版本、主要变更、已知问题和回滚方式。

涉及积分、支付、认证、权限或任务状态的变更不得无监控直接发布。紧急修复上线后必须补齐测试和变更记录。

## 17. 默认技术决策与待确认项

以下是项目启动时的默认建议，不属于不可修改规则：

| 模块 | 默认建议 | 说明 |
| --- | --- | --- |
| Web 框架 | Next.js + TypeScript | 适合工作台、认证和服务端能力整合 |
| 样式 | Tailwind CSS + 设计令牌 | 便于快速实现并保持一致性 |
| 组件 | Radix UI 或同类无样式组件 | 保留品牌定制能力和可访问性 |
| 数据库 | PostgreSQL | 适合用户、任务、积分和订单事务 |
| ORM | Prisma 或 Drizzle | 在项目初始化时二选一 |
| 队列 | Redis + BullMQ 或托管队列 | 视频任务必须异步执行 |
| 对象存储 | S3 兼容存储 | 保存上传图片和生成视频 |
| 认证 | 成熟认证服务或 Auth.js | 不自行实现会话安全细节 |
| 支付 | 按目标市场选择 | 国内与海外支付需分别评估 |
| 模型 | 一个稳定的图生视频 API | MVP 不同时维护多个供应商入口 |
| 监控 | 错误追踪 + 结构化日志 | 必须能按任务 ID 追踪 |

开始编码前仍需明确：

- 首发市场是中国大陆、海外还是同时覆盖
- 登录方式和邮件服务
- 首个视频模型供应商及其内容政策
- 对象存储和 CDN
- 免费积分、水印及套餐定价
- 支付渠道和结算货币
- 素材与结果的实际保留期限
- 品牌名称、Logo、主色和字体

## 18. 决策优先级

发生冲突时按以下顺序决策：

1. 用户数据、安全、法律和支付正确性。
2. 核心生成闭环可用性。
3. 生成成功率、失败恢复和成本控制。
4. 页面清晰度、响应式和可访问性。
5. 视觉精致度和非核心动效。
6. 尚未验证的扩展功能。

任何“看起来更像参考网站”的调整，都不能覆盖用户数据安全、独立品牌、核心流程和成本控制要求。
